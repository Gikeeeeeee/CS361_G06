# Smart Faculty Navigator


## Project Vision

เป็นระบบกลางที่ช่วยให้คนในคณะตอบได้ว่า "ต้องไปที่ไหน เมื่อไร และไปอย่างไร" จากระบบเดียว โดยเริ่มจากข้อมูลสถานที่ (Information Service) แล้วค่อยๆ ขยายไปสู่ข้อมูลตารางเรียน/ตารางสอบ/กิจกรรม การค้นหาตามวัตถุประสงค์ การนำทาง และการเชื่อมกับปฏิทินส่วนตัว ในเวอร์ชันถัดไป



## Primary User

**บุคคลภายในคณะ (Internal Users)**

* นักศึกษา, อาจารย์ และเจ้าหน้าที่ ที่ต้องการเดินทางไปยังห้องหรือจุดบริการที่ตนไม่คุ้นเคย
* ใน V1 เนื่องจากระบบไม่มีการยืนยันตัวตน (No Authentication) จึงจัดกลุ่มผู้ใช้ทั้ง 3 บทบาทเป็นผู้ใช้กลุ่มเดียวกัน เนื่องจากมีความต้องการข้อมูลสถานที่ในรูปแบบ Read-Only เช่นเดียวกัน
* ช่วยอำนวยความสะดวกสำหรับผู้มาใหม่ หรือผู้ที่ไม่สะดวกถามข้อมูลจากผู้อื่นโดยตรง (Introvert-friendly)

*หมายเหตุ: ตัดกลุ่มบุคคลภายนอกออกจาก V1 เพื่อจำกัดขอบเขตข้อมูลที่ต้องเผยแพร่และจัดเก็บ*


## Problem

**Current Situation**
เมื่อบุคคลภายในไม่รู้ว่าห้องอยู่ที่ไหนหรือห้องนั้นมีอะไรบ้าง สิ่งที่ทำในปัจจุบันคือ:
* เดินไปถามเจ้าหน้าที่ หรือถามเพื่อน/เพื่อนร่วมงาน
* ดูผังอาคารที่ติดอยู่ตามอาคาร ซึ่งดูได้เฉพาะตอนไปถึงสถานที่นั้นแล้ว
* เดินหาเองหรือเดินวนหลายชั้นจนกว่าจะเจอ

**Problem Statement**
บุคคลภายในคณะไม่สามารถรู้ล่วงหน้าได้ว่า ห้องหรือจุดบริการที่ตนต้องไปนั้นอยู่บริเวณใด และมีสภาพหรือสิ่งอำนวยความสะดวกอะไรบ้าง ทำให้ต้องพึ่งพาการถามคนอื่นหรือเดินหาหน้างาน และไม่สามารถวางแผนการเดินทางล่วงหน้าได้

**Desired Outcome**
* บุคคลภายในสามารถค้นหาข้อมูลอาคาร ห้อง และจุดบริการได้ด้วยตัวเองตลอดเวลา
* วางแผนล่วงหน้าก่อนออกเดินทางได้ (เช่น รู้ว่าห้องมีแอร์จึงเตรียมเสื้อกันหนาว)
* ลด Workload ของเจ้าหน้าที่ในการตอบคำถามเดิมๆ เรื่องตำแหน่งห้อง


## V1 Goal

ให้บริการข้อมูลสถานที่และจุดบริการแบบ Read-Only โดย ไม่ต้องเข้าสู่ระบบ (No Authentication Required) โดยเน้นขอบเขตพื้นที่เฉพาะ **อาคาร บร.3 และ บร.4** เพื่อให้ผู้ใช้ค้นหา ค้นพบ และทำความเข้าใจตำแหน่งของจุดหมายได้ด้วยตนเองก่อนเดินทางไปถึง

* รองรับการใช้งาน 2 ภาษา (TH / EN)
* ข้อมูลเน้นรูปแบบ Static Information ที่มีความแม่นยำสูง


## V1 In Scope

* **Building Name:** ชื่ออาคาร (เน้น บร.3 และ บร.4)
* **Room Name:** ชื่อและรหัสห้อง (เช่น บร.3-121)
* **Room Feature:** รายละเอียดภายในห้อง (เช่น มีแอร์, ห้องคอมพิวเตอร์, จำนวนที่นั่ง)
* **Building Facility:** จุดอำนวยความสะดวก (เช่น ห้องน้ำ, จุดกดน้ำ, ลิฟต์)
* **Building Plan:** ผังอาคาร/ผังแสดงพื้นที่ในแต่ละชั้น
* **Room Image:** ภาพถ่ายบรรยากาศหรือรูปหน้าห้องประกอบ

## V1 Out of Scope

* ระบบรีวิว หรือการให้คะแนนห้องพัก/สถานที่ (Review / Rating)
* ข้อมูลกิจกรรม ตารางสอบ หรือตารางเรียน (Event / Timetable)
* ระบบสมาชิก ล็อกอิน หรือการแบ่งสิทธิ์ผู้ใช้ (Authentication / Roles)
* ระบบนำทางแบบ Turn-by-Turn หรือ Real-time Indoor Positioning
* การเชื่อมต่อกับปฏิทินส่วนตัว (Calendar Export)
* ระบบ Back-office ให้เจ้าหน้าที่แก้ไขข้อมูลผ่านหน้าจอ (V1 ใช้การนำเข้าข้อมูลแบบ Manual โดยทีมงาน)
* อาคารอื่นๆ นอกเหนือจาก บร.3 และ บร.4

## External Actors / Systems

* **Data Owners / Providers:**
  * ผู้ดูแลอาคาร, สำนักทรัพย์สิน, กองบริหารงานอาคาร, กองกิจการนักศึกษา
  * คณะวิทยาศาสตร์ (หน่วยงานผู้ดูแลอาคาร บร.1 - บร.4)
* **Map Service:**
  * บริการแผนที่ภายนอก (เช่น AWS Location Service หรือ Google Maps API)
* **System Admin / Internal Team:**
  * ทีมพัฒนาทำหน้าที่เป็นผู้บริโภคข้อมูล (Data Consumer) ที่ต้องลงพื้นที่สำรวจและจัดทำรวบรวมข้อมูลต้นทางเข้าสู่ระบบ

## Open Questions / To Validate

1. **User Validation:** ทั้งสามบทบาท (นศ./อาจารย์/เจ้าหน้าที่) มีปัญหาเรื่องการหาห้องเหมือนกันจริงหรือไม่ หรืออาจารย์/เจ้าหน้าที่คุ้นเคยพื้นที่อยู่แล้ว
2. **Data Owner:** ใครคือเจ้าของข้อมูลอาคาร บร.3–บร.4 ตัวจริงที่มีอำนาจอนุมัติข้อมูล
3. **Data Format:** เจ้าหน้าที่มีไฟล์ข้อมูลห้องและผังอาคารในรูปแบบใด (PDF / Excel / CAD / รูปภาพ) และพร้อมส่งมอบเมื่อไร
4. **Data Collection Effort:** หากไม่มีไฟล์ข้อมูลต้นทาง ทีมต้องลงพื้นที่สำรวจเองมากน้อยเพียงใดและใช้เวลาเท่าไร
5. **Information Priority:** ข้อมูลส่วนใดที่ผู้ใช้จำเป็นต้องรู้มากที่สุด (ตำแหน่งห้อง vs สิ่งอำนวยความสะดวก vs รูปถ่ายห้อง)
6. **Data Sensitivity:** ผังอาคารมีจุดใดที่ไม่ควรเปิดเผยต่อสาธารณะหรือไม่ (เช่น ห้องเซิร์ฟเวอร์, ห้องเก็บสารเคมี)
7. **Data Change Frequency:** ข้อมูลสถานที่และผังห้องมีการเปลี่ยนแปลงบ่อยแค่ไหนในความเป็นจริง
